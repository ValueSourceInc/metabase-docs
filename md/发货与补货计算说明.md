# 发货与补货计算说明

> 本文按当前生效逻辑编写。最终以 Metabase 卡片实际 SQL 为准。

## 1. 一句话看懂链路

```text
#806 库存修正 + #954 历史日销 + #876 每日预测
                              ↓
                         #877 基础数据 ──┐
 #876 预测（未开卖 SKU 凭此入表）───────┤
 #899/#900 异常货件、#1208 状态模型 ────┤
                                        ↓
                               #878 计算引擎
                                        ↓
                   #873 发货/补货展示（结果来自 #878）
                                        ↓
                   #901 工厂补货（SKU 粒度）
                              ↓
                               #985 批次发货表
                              
              #1192 → #1201 → #1180（工厂 SKU 粒度）
```

- `#878` 计算 FBA 理论发货量 `need_to_ship` 和实际分配量 `allocated_qty`。
- `#873` 主要展示 #878 的结果。
- `#901` 按 SKU 粒度计算工厂生产量，并叠加 #1085「当前有效工厂补货计划」（由 #1084 运营表筛出）。
- `#1192` 将 #873 的需求、库存和退货在 `factory_sku` 粒度合并后重新计算需产；`#1201` 是带状态的展示层；`#1180` 在此基础上执行工厂 MOQ/凑单规则。
- `#985` 批次发货表，按批次展示 #878 的发货结果。「销售天数」列（`first_sale_days_diff`，来自 #1208 的 today−首单日期）2026-09-08 起未售出 SKU 显示 0 而非空白（coalesce；原 NULL 表示"从未售出"，语义不变——0 在此列表示该站点尚未出单）。
- 进表条件（2026-08-25 起）：#877 行集合 ∪ #876 配置了未来 `daily_sales>0` 的 SKU——新品开卖前、断货超 30 天的 SKU 都在表里，详见 2.6。

## 2. 预测表怎么影响系统

预测表按 `sku + store + marketplace + 日期` 生效。同一天多条记录时，`priority` 大的优先；同 priority 取 `id` 大的。

### 2.1 当前规则

| 配置                         | 历史基线（#954） | 未来预测（#876/#878）                                                               |
| ---------------------------- | ---------------- | ----------------------------------------------------------------------------------- |
| `event` + `daily_sales > 0`  | 该日期完全剔除   | 使用手填日销；有倍率则再相乘                                                        |
| `event` + `daily_sales = 0`  | 该日期完全剔除   | 日销为 0，不产生新的需求                                                            |
| `event` + 日销为空、倍率有值 | 该日期完全剔除   | 干净历史日销 × 倍率                                                                 |
| `event` + 日销和倍率都为空   | 该日期完全剔除   | 不改变未来日销（**断货期修复基线专用**：断货日不配会按 0 计入拖低基线，配上就剔出） |
| 无标签或其他标签             | 按实际订单       | 按配置的日销/倍率生效                                                               |

核心原则：**任何 `event` 日期都不进入历史基线，包括停产的 `daily_sales=0`。预测表的手填日销不会被写入历史基线。**

### 2.2 活动跨过今天的例子

今天是 8 月 24 日，配置：

```text
start_date=8月15日, end_date=8月30日
forecast_type=event, daily_sales=100
```

结果：

- 8/15-8/23：订单仍按实际展示，但这些日期不进入历史基线；
- 8/24-8/30：未来按 100/天预测；
- 8/31 以后：活动失效，恢复使用排除活动后的历史日销。

因此圣诞节日销 100 不会在活动结束后抬高补货基线。

### 2.3 倍率活动例子

```text
forecast_type=event, daily_sales=NULL, multiplier=5
start_date=11月19日, end_date=11月30日
```

活动期间按“干净历史日销 × 5”预测，活动日期不参与历史平均；活动结束后回到干净历史日销。

### 2.4 停止未来自动发货

```text
start_date=过去日期
end_date=NULL
forecast_type=event
daily_sales=0
multiplier=NULL
priority=999
```

从开始日以后未来日销为 0，#878 的未来需求不再增长，自动 `need_to_ship` 应为 0，#873 不产生新的自动发货量。停产日不进入历史平均，所以不会把历史基线直接算成 0。

`end_date=NULL` 会持续到当前预测规划期末；同日若有其他配置，停产记录应使用最高 priority 防止被覆盖。US、CA 要分别配置。

### 2.5 过渡期日销

预测表已删除 `recovery_daily_sales` 和 `recovery_days`。如果活动后 30 天想按 0.1/天预测，另建：

```text
start_date=活动结束次日, end_date=结束后第30天
forecast_type=event, daily_sales=0.1
```

这段日期同样不进入历史基线。

### 2.6 预测配置决定哪些 SKU 进补货表（2026-08-25 起）

#878 的行集合不再只来自 #877（近 30 天有订单），新增一支 UNION：

```text
入表 = #877 行集合
     ∪ #876 中满足以下条件的 sku + store + marketplace：
       · forecast_date ≥ 今天（仍有未来覆盖）
       · daily_sales > 0（有实际预测需求）
       · 不在 #877 中（防重复）
       · sku 非空、非 amzn 开头
```

- **新品**：在 #876 配好「新品推广」日销后，开卖前就出现在 #873/#985/#901。日销按配置值，FBA 库存按 0，工厂库存取 #990（casepack/moq 取自 wps_product），`need_to_ship` 按配置日销推算，`allocated_qty` 受工厂库存约束。若配置 `min_shipment_quantity>0`，`need_to_ship` 最低为该值（2026-08-28 起，见 5.2）。**零库存新品的 `wos_now` 显示真实首个需求日推算的断货周数**（如预测 9/8 开始则约 2 周），不再显示兜底值 100（2026-08-25 修复：库存 0 且当天无日销时，除法得 NULL 落到 700/7 兜底）。
- **断货超过 30 天的 SKU**：以前会因「近 30 天无订单」从表里消失；现在只要还有未来预测配置就保留。
- **不进表**：纯倍率（`daily_sales` 为空）或 `daily_sales=0` 的配置，对无历史的 SKU 产生不了需求，不占行。
- 注意：#879「未来有效日销」model 仍是旧宇宙（只含 #877 行），尚未同步此改动。

背景：此前 #876 里 63 个 SKU（其中 54 个「新品推广」）的预测配置是孤儿数据--forecast 只是 LEFT JOIN 到 #877 的行上，SKU 不在 #877 就被静默丢弃，新品要等首单卖出才进补货体系。

## 3. #954 历史日销怎么算

- 默认窗口是昨天往前 30 个自然日；新品从首个有订单日期开始。
- 正常日期按自然日计算，没卖出记 0。
- 所有 event 日期分子、分母都不算。
- 有效日不足 7 天时，最多回看 90 天，补取最近 30 个非 event 日；没有有效日时结果为 0。

所以停产日期被排除，不会把日销压成 0；只有完全没有正常销售数据时，基线才为 0。

常用字段：

| 字段                           | 含义                                    |
| ------------------------------ | --------------------------------------- |
| `promo_excluded_sales_per_day` | 排除 event 后的干净历史日销，补货使用它 |
| `normal_days_sold`             | 实际参与计算的有效日数                  |
| `promo_day_ratio`              | 最近 30 天 event 占比                   |
| `raw_sales_per_day`            | 未排除 event 的对照值                   |

检查活动污染时，对比 `raw_sales_per_day` 与 `promo_excluded_sales_per_day`。

## 4. #806 库存修正

#806 识别加拿大库存中可能重复映射的美国镜像行。下游统一使用 `adjusted_*`，不用 MYI 原始值。判定证据来自 MYI、Remote Fulfillment Eligibility、Ledger Summary。

主要标记：

| 标记                               | 含义                         | 处理                                      |
| ---------------------------------- | ---------------------------- | ----------------------------------------- |
| `US_MARKETPLACE`                   | 美国行                       | 原样保留                                  |
| `LOCAL_STOCK`                      | 加拿大有真实本地库存         | 仓库/可售取库存与 Ledger 较小值，在途保留 |
| `NOT_WHITELISTED`                  | Remote 明确表示本地 FBA 互斥 | 原样保留                                  |
| `MIRROR` / `MIRROR_LAG`            | 加拿大是美国镜像             | 相关列按 CA−US 修正                       |
| `MIRROR_NOT_ELIGIBLE`              | Remote 不合格但证据显示镜像  | 同镜像处理                                |
| `FFQ_EQ_COINCIDENCE` / `NO_US_ROW` | 证据不足                     | 只标记，不修                              |
| `EXCLUDED_AMZN`                    | `amzn` 开头的 SKU            | 按设计排除                                |

镜像行修正公式：

```text
adjusted_value = GREATEST(CA原始值 - US原始值, 0)
```

该公式也用于在途列，不能直接把在途清零；CA−US 的差额可能是真实发往加拿大的货。Remote 报表的国家列顺序因店铺可能不同，#806 应自动识别，不要写死 `Offer status` 或 `Offer status_2`。

## 5. #878/#873：发多少货

### 5.1 未来有效日销

```text
有配置且 daily_sales 不为空 = daily_sales × multiplier（倍率空按1）
有配置但 daily_sales 为空     = 历史基线 × multiplier
没有配置                      = 历史基线
```

因此 `event + daily_sales=0` 明确得到 0，不会回退到历史日销。未开卖的新品行（见 2.6）历史基线为 0，未来日销完全由 #876 配置决定。

### 5.2 `need_to_ship` 理论发货量

系统逐日模拟：

1. 当前库存到发货到达前会卖掉多少；
2. 到货时还剩多少可用库存；
3. 到货后安全库存期还会消耗多少；
4. 期间最大缺口是多少。

简化公式：

```text
need_to_ship = CEIL(MAX(到货后安全期累计需求 - 到货时库存, 0))
```

`need_to_ship_with_casepack` 再向上凑整箱。

**新品首次最低发货量 `min_shipment_quantity`（2026-08-28 起）：** 预测表
`wps_sales_forecast` 新增列 `min_shipment_quantity`（#875/#876 同步带出），作为新品首次发货的
最低发货量。对 #878 的新品分支（2.6 的 UNION 行：在 #876 有未来 `daily_sales>0`、不在 #877），
当该值 > 0 时：

```text
need_to_ship = MAX(原计算值, CEIL(min_shipment_quantity))
```

分配目标 `need_qty` 取同一下限，`need_to_ship_with_casepack` 在该下限之上凑整箱，因此
`allocated_qty` 也向该下限靠拢，但仍受工厂库存、`shipment_cap`、整箱约束截断（库存不足时
发不到最低量）。#877 老品行不适用此下限（该分支 `min_shipment_quantity` 恒为 0）。

`shipping_days` / `safety_wos` 在 #877 配置：**当前生效 US=45 天 / CA=60 天船期 + 15 天安全（safety_wos=15/7≈2.14 周）**。SQL 内的 30 天 / 30 天只是空值兜底，不是当前值。

逐日模拟的地平线按 SKU 截断（2026-08-25 起）：每个 SKU 只逐日模拟到 `min(700, max(船期+安全期, 最后预测日)+1)` 天，之后的恒定日销尾巴用解析公式补（数学上与逐日扫描完全等价），大幅降低 #878 计算量。

停产后 `effective_daily_sales=0`，未来需求不增长，自动 `need_to_ship` 应为 0。若停产开始日是未来日期，开始前仍可能产生发货需求，这是正确的。

### 5.3 `allocated_qty` 实际分配量

理论需求还要受：

1. SKU/店铺工厂库存；
2. `parent_asin × Marketplace` 发货上限（默认 750）；
3. SKU 自身需求；
4. `casepack` 整箱约束。

系统先按 `wos_now` 从小到大满足救急需求，再补普通需求。救急阶段的目标窗口是 `safety_days × safety_wos_ratio`（#878 可调参数，默认 1.0 即补满整个安全期）；`shipment_cap`（默认 750）同样是 #878 参数。工厂库存按 SKU+店铺共享，US/CA 会竞争同一库存池；发货上限按 parent+站点分别计算。

```text
allocated_qty <= need_to_ship
allocated_qty <= factory_in_stock
```

所以 `need_to_ship` 有值而 `allocated_qty=0`，通常是工厂库存、发货上限或整箱约束造成的。

## 6. #901：工厂生产量

### 6.1 单站点

```text
站点生产需求
= need_to_ship
 +（生产周期 + 工厂安全库存半周期）× 站点日销
```

工厂安全库存默认按 1 周的一半，即 3.5 天折算。

生产周期、工厂库存、MOQ 三个量按 **US 优先**取值：US 为 0 才取 CA（同一 SKU 共享一套配置）；`need_to_ship` 和日销则各站点独立。

### 6.2 总生产需求

```text
total_need_to_produce
= MAX(US生产需求 + CA生产需求 - 工厂库存 - return_ship退货在途, 0)
```

### 6.3 MOQ

```text
需求 >= MOQ       -> 按需求生产
需求 >= MOQ×70%   -> 按 MOQ 生产
需求 < MOQ×70%    -> 本轮不生产
```

实际下单优先看 `final_adjusted_need_to_produce_with_moq`。

### 6.4 #1084 工厂补货计划

#901 实际读取 #1085「当前有效工厂补货计划」--它在 #1084 基础上筛选 `start_date <= 今天 <= end_date`。同一 SKU+店铺重叠时 priority 大的优先，同 priority 取最新记录。

```text
multiplier=0              -> 停止生产
specified_quantity 有值   -> 使用指定生产量
multiplier 有值           -> 系统需求 × multiplier
否则                      -> 使用系统需求
```

这张表只调整工厂生产，不停止 FBA 自动发货。要同时停止发货，预测表也要配置 `event + daily_sales=0`。已有人工生产计划不会自动删除。

### 6.5 清仓周数 weeks_to_clearance（#921 清仓表）

```text
weeks_to_clearance = 工厂库存 stock ÷ (total_raw_daily_sales × 7)
total_raw_daily_sales = US + CA 的 raw_sales_per_day 之和（未排除 event 的实际日销，见第 3 节）
```

#901 的 `weeks_to_clearance` 列与下游 #921「清仓表」的 `week_to_clearance` 同口径；#921 的
`estimated_total_days_to_clearance` = stock ÷ total_raw_daily_sales，再 ÷7 得周数。
#921 清仓表入选条件：US/CA adjusted_days_sold 均 >60 天，且 week_to_clearance >30。

**2026-08-27 起改用 raw 实际动销口径**（#901 同日新增 `total_raw_daily_sales` 列）。此前用
`total_estimated_daily_sales`（剔促销基线），促销剔除上线（2026-08-21）后失真：促销重度 SKU
周数虚高（实测头部 137~605 周），纯促销 SKU 基线为 0 直接被排除出清仓表。切换当天清仓表
61 个 SKU 降至 51 个，移出的均为靠促销撑销量的 SKU。

口径分界：清仓周数看**实际动销**（含促销）；补货预测（wos_now / need_to_ship 等）仍用
**剔促销基线**，两者不要混用。raw 日销为 0 且有工厂库存时周数记 **999（哨兵值，2026-08-27 追加）**——
彻底卖死的 SKU 曾因周数为空被 `>30` 过滤器静默排除；无工厂库存时周数为空，不进表。

### 6.6 补货基础表 #1192（factory_sku 粒度，2026-09-04 上线）

`wps_product` 新增 `factory_sku` 字段后，工厂链以 **#1192「补货基础表 (工厂SKU)」**（model，
native SQL，引用 #873 + #1085 + #1182 工厂SKU映射）为基表：把补货明细聚合到物理产品粒度，
**一个 factory_sku 一行，无 moq 列**（MOQ 留给 #1180 批次表按款式算）。**#901 不动**（sku 粒度，
921 清仓表 / 960 / 指标口径继续用它）。

- **合并键 = factory_sku**（#1182 引入 `wps_product.factory_sku`）：一个工厂 SKU
  对应一个物理产品，覆盖 DH/VS 双店同名款**和同店换 SKU**，直接按 factory_sku GROUP BY。
  前提：WPS 新增 SKU 时必须同步填 factory_sku，未填的 SKU 不会出现在本表
- **factory_sku 统一口径（2026-09-07 起）**：`wps_product.factory_sku` 按用户定稿的
  颜色码表统一（BR=棕、IV=象牙白、BG=米白、OL=橄榄绿、GN=绿、BE=蓝、CF=咖啡
  ——**CF≠BR 不合并**、WH=白废"纯白"；GY 仅 CS001/CTN_SATN=蓝灰其余=灰；
  BU 水洗系 DD002/ST002=浅蓝其余=蓝；尺寸 XL-TH 改 **TH_XL** 下划线写法）。
  影响：原本按旧 fs 写法分散/错并的组重归位（麻花辫"咖啡"与"棕"分家、树叶毯
  DH/VS 同物理产品正确合并、米白/橄榄绿统一命名），当天实测 1192 为 269 组、
  1180 为 60 行。工厂合同 desc 不改，仍保留旧色词属正常
- **#1182 附 `sku_status` 列**（2026-09-04 起**四态**，信号源 = **#1208 状态模型**
  （聚合到 sku×店，任一市场有信号即算；store 列同日改 DH/VS 简码）：
  下架 = `wps_product.inactive` **或** 1085 停产计划生效行（multiplier=0 或
  specified_quantity=0，按 SKU 匹配，只标有计划行的 SKU——同 fsku 无计划行的
  不扩散，如未上架的 CS001 仍算新品）；在卖 = `sku_is_selling`（本 SKU 有
  SELLABLE 收货记录，自己入过仓）；**新变体 = `parent_sku_is_selling` 且非
  `sku_is_selling`**（parent 家族在卖、本变体还没入仓——当日数据 0 行，留给
  876 新配置变体用）；新品 = 两者皆无（含 876 已配置未发货的，如麦穗毯；
  **不在 #1208 宇宙的链外 SKU 也归新品**——当日 1 行 QS-VT001-K-PK 从在卖
  翻新品，因其无近期销量且无 876 配置、落在 1208 宇宙外）。仅参考列，
  不参与任何计算。状态数量会随订单、收货和 WPS 配置变化，不在本文固定记录快照。
- **数据源 = #873**（补货明细，sku×店×市场行）：先透视到 sku×店（US/CA 各市场列求和，
  need_to_ship/estimated_daily_sales/raw_sales_per_day/return_ship_quantity；工厂库存与生产周期
  按 US 非零否则 CA 择一，同 901 口径；days_sold = us/ca 调整值取大），再按 factory_sku 合并
- **聚合语义**：us/ca_need_to_ship、us/ca 日销、raw 日销、工厂库存、退货在途 = **SUM**；
  生产周期、days_sold、颜色、尺寸、规格 = 组内 MAX（品名优先 DH 店）
- **需产在组粒度计算**：
  `us/ca_need_to_produce = CEIL(Σ需发货 + 生产周期 × Σ日销)`（各操作数先转 double precision
  再运算，精确对齐 901 的 float 算术边界值）；
  `total_need_to_produce = max(us + ca − Σ工厂库存 − Σ退货在途, 0)`，**合并后才钳 0**——

## 7. 完整算例

假设 US SKU：当前可用库存 205、异常在途 20、`shipping_days=30`、`safety_days=30`、未来日销 5。（船期/安全期取 30/30 便于口算；当前实际生效 US 45 / CA 60 天船期 + 15 天安全，见 5.2。）

```text
到货前需求 = 30×5 = 150
到货时库存 = 205-150-20 = 35
到货后安全期需求 = 30×5 = 150
缺口 = 150-35 = 115
need_to_ship = CEIL(115) = 115
```

若 `casepack=12`：

```text
need_to_ship_with_casepack = CEIL(115/12)×12 = 120
```

若工厂只有 100 件：

```text
allocated_qty = FLOOR(MIN(115,100)/12)×12 = 96
```

理论需求仍为 115；实际本票只能分配 96。生产端按理论需求和生产周期计算，避免因本次发不够而漏算后续生产。

## 8. 两种“停止”不要混淆

| 目标                   | 配置                                                          |
| ---------------------- | ------------------------------------------------------------- |
| 停止某站点未来自动发货 | 预测表：`event + daily_sales=0 + end_date=NULL + 高 priority` |
| 停止工厂生产           | #1084：`multiplier=0` 或指定量 `0`                            |
| 两者都停止             | 两张表都配置                                                  |

### 为什么今天的活动仍显示实际销量？

历史订单不会被改写；event 只影响未来预测和历史基线是否纳入。活动已发生的日期仍应展示真实订单。

## 10. 维护检查

1. US、CA 必须分别配置，`sku/store/marketplace` 要准确。
2. 重叠配置必须明确 priority；停产配置建议用 999。
3. 活动结束后建议保留 event 记录至少 90 天，避免历史窗口回看时失去排除依据。
4. 不要把 `allocated_qty` 当成生产需求，生产使用理论 `need_to_ship`。
5. 不要把镜像行在途直接清零，镜像修正使用 CA−US。
6. 变更后依次核对 #954、#877、#878、#873、#901、#1192、#1201、#1180 的关键字段：`promo_excluded_sales_per_day`、`effective_daily_sales`、`need_to_ship`、`allocated_qty`、`total_need_to_produce`、`final_adjusted_need_to_produce`；工厂下单还要核对 MOQ 分组、补足量和建议下单量。
7. 无标签 + `daily_sales=0` 同样会停未来发货，但 0 销日会按 0 计入基线把它越拖越低；停产请用 `event+0`（剔出基线，保住停产前水平）。注意 901 的安全项仍按非零基线计算，当前全被 70% MOQ 线拦住是巧合，不是机制保障。
8. 新品或断货 SKU 要进补货表，必须在 #876 配置未来 `daily_sales > 0`；纯倍率、0 日销配置不会入表（见 2.6）。`sku/store/marketplace` 同样要配准，US、CA 分开出。
